その方針で組むのがいい。**対応情報は親フォルダに置かず、アプリ専用の永続領域に置く。ただし Windows の `%TEMP%` には置かない**、が結論。

`TEMP` は消されてもおかしくないので、「次回起動して編集済みJSONをJARへ戻す」ための対応情報には向かない。今のアプリは設定をすでに `%LocalAppData%\ModLangOrganizer` 配下へ保存しているので、対応情報も同じ系統にまとめるのが自然。

例えばこうする。

```text
%LOCALAPPDATA%\ModLangOrganizer\
├ settings.json
└ workspaces\
   ├ 7A4D93C1...\
   │  └ mapping.json
   └ C88102F5...\
      └ mapping.json
```

`7A4D93C1...` は選択したMOD親フォルダの正規化パスから作ったハッシュなどでいい。

---

## 実装方針

アプリの中心を、

```text
JARをスキャン
    ↓
編集しやすい場所へlangを抽出
    ↓
対応情報をアプリ内部に保存
    ↓
ユーザーがJSON編集
    ↓
対応情報を使って元JARの正確な場所へ戻す
```

にする。

リソースパックは削除せず、**署名付きJARなど直接変更できない場合の代替手段**に降格する。

---

## 1. 編集フォルダを再び簡略化する

基本形はこれでいい。

```text
翻訳作業フォルダ/
├ carbonconfig/
│  └ ja_jp.json
├ cloth_config2/
│  └ ja_jp.json
├ curios/
│  └ ja_jp.json
└ libipn/
   └ ja_jp.json
```

ユーザー側には、

```text
assets/
  modid/
    lang/
```

を見せない。

現在は `LangPathResolver` がJAR名を外部フォルダ名として使う仕組みになっている。

ここを新方式では、

```text
<OutputRoot>/<ModId>/<filename>
```

を基本にする。

ただし同じMod IDが複数JARから出た場合だけ、

```text
curios/
curios__some-embedded-mod/
```

のように衝突回避する。

**通常ケースを複雑な構造にして衝突を避けるのではなく、衝突した時だけ複雑にする**方がいい。

---

## 2. mapping.json を新設する

例えば内部的にはこういう情報を持つ。

```json
{
  "schemaVersion": 1,
  "targetRoot": "D:\\Minecraft\\instance\\mods",
  "entries": [
    {
      "editPath": "carbonconfig/ja_jp.json",
      "jarRelativePath": "carbonconfig-forge-1.20.1-xxx.jar",
      "modId": "carbonconfig",
      "archivePath": "assets/carbonconfig/lang/ja_jp.json"
    },
    {
      "editPath": "curios/ja_jp.json",
      "jarRelativePath": "curios-forge-5.x.jar",
      "modId": "curios",
      "archivePath": "assets/curios/lang/ja_jp.json"
    }
  ]
}
```

ここで一番重要なのが、

```text
editPath
↓
jarRelativePath
↓
archivePath
```

の3つ。

JAR反映時に**フォルダ名からMod IDやJAR内パスを推測しない**。

現在のImporterも `ArchiveLangPath` を使って正しいJAR内パスを構築する設計なので、その思想を永続化する形になる。

---

## 3. mapping.json はキャッシュではなく「永続作業情報」にする

ここは少し重要。

名前としても `temp` や `cache` より、

```text
workspaces
```

の方が実態に合う。

例えば、

```text
%LOCALAPPDATA%\ModLangOrganizer\
└ workspaces\
   └ <workspace-id>\
      ├ mapping.json
      └ mapping.json.bak
```

とする。

書き込みだけは、

```text
mapping.json.tmp
↓
正常に書けた
↓
mapping.json と置換
```

という一時ファイル方式にする。

つまり、

**保存場所は永続領域**
**更新処理だけ一時ファイル**

にする。

---

## 4. JAR反映はmappingを唯一の正解にする

ここは今回の変更の中核。

現在の `JarLangImporter.CreatePlan()` は、スキャン結果から外部フォルダを求め、そこに存在する `.json/.lang` を列挙してJAR内パスを組み立てている。

新方式では、

```text
mapping.json
      ↓
編集ファイルが存在するか
      ↓
対象JARが存在するか
      ↓
スキャン時とJARが対応しているか
      ↓
archivePathへ反映
```

に変更する。

例えば、

```text
carbonconfig/ja_jp.json
```

しか見えていなくても、

```text
mapping:
  jar = carbonconfig-forge-xxx.jar
  archivePath = assets/carbonconfig/lang/ja_jp.json
```

なので確実に戻せる。

---

## 5. mappingが無い場合は「推測して反映」しない

これは安全策として必須。

例えばユーザーが手作業で、

```text
foobar/
└ ja_jp.json
```

を置いたとしても、

> foobarだから `assets/foobar/lang/ja_jp.json` だろう

とは判断しない。

UI上では、

```text
未関連付け
```

として扱う。

必要なら再スキャンして対応情報を生成する。

これによって誤JAR・誤namespaceへの書き込みをかなり防げる。

---

## 6. スキャン時にmappingを再検証する

mappingを永久に信用するのも危ない。

例えばMODを、

```text
carbonconfig-1.2.jar
↓
carbonconfig-1.3.jar
```

へ更新したら、古いJAR名を指しているmappingはそのまま使えない。

そこでスキャン時に、

```text
Mod ID
ArchiveLangPath
対象JAR
```

を再照合する。

同一MODの新しいJARを見つけて、

```text
旧
carbonconfig-1.2.jar

新
carbonconfig-1.3.jar
```

になった場合、

```text
carbonconfig/ja_jp.json
```

自体はそのまま残して、

```text
mappingだけ
1.2.jar → 1.3.jar
```

へ更新する。

これ、かなり使い勝手が良くなる。

**MODをアップデートしても翻訳JSONを作り直さなくていい。**

---

## 7. ただし自動再関連付けには条件を付ける

Mod IDだけ一致したから自動で付け替える、は少し危ない。

少なくとも、

```text
ModId一致
+
assets/<同じnamespace>/lang が存在
```

くらいまでは確認する。

できれば、

```text
旧 archivePath
assets/carbonconfig/lang/ja_jp.json
```

に対して新JARにも、

```text
assets/carbonconfig/lang/
```

が存在するか確認する。

一致しなければ、

```text
⚠ 対応先を再確認してください
```

にする。

勝手に別パスへ移行しない。

---

## 8. fallbackで作った ja_jp もmappingへ登録する

今のlangフォールバック、

```text
en_us
↓
ja_jp
```

もこの仕組みにかなり向いている。

例えば元JARには、

```text
assets/example/lang/en_us.json
```

しかない。

抽出側では、

```text
example/
└ ja_jp.json
```

を作る。

mappingは、

```text
editPath:
example/ja_jp.json

archivePath:
assets/example/lang/ja_jp.json
```

にする。

つまりJARに元々 `ja_jp` が存在しなくても問題ない。

---

## 9. 既存の編集ファイルは絶対に自動移動しない

「以前のファイルを壊さない」ならここは強く守った方がいい。

アップデート直後に、

```text
旧:
PuzzlesLib-v8.1.33-1.20.1-Forge/
  ja_jp.json
```

を勝手に、

```text
新:
puzzleslib/
  ja_jp.json
```

へ移動しない。

最初のスキャンで旧形式を検出したら、

```text
mapping.editPath =
"PuzzlesLib-v8.1.33-1.20.1-Forge/ja_jp.json"
```

として**そのまま登録する**。

つまり既存環境では見た目も動作も変えない。

新しく抽出するMODから、

```text
puzzleslib/ja_jp.json
```

形式を使う。

あとから必要なら、

```text
編集フォルダを新形式へ整理
```

という明示的な移行機能を別途作れる。

最初の実装には要らない。

---

# リソースパック機能の扱い

削除まではしない方がいい。

画面上では今の、

```text
[langを抽出]
[リソースパック出力（推奨）]
[JARへ反映]
```

から、

```text
[langを抽出]    [JARへ反映]

その他の出力 ▼
  リソースパックとして出力
```

に変える。

そして署名保護でJAR反映できなかった場合だけ、

```text
Configured は署名保護のためJARへ直接反映できません。

[リソースパックとして適用]
```

を出す。

現在も署名保護でブロックされた場合、リソースパック利用を案内する処理がすでにあるので、その延長で実装できる。

---

# リソースパックの毎回フォルダ選択も直す

残すならここも同時に直した方がいい。

現在はリソースパック出力ごとに配置先フォルダを選択して、その中に `ModLangOrganizer Translations` を作る方式。

`AppSettings` に、

```text
ResourcePackOutputRoot
```

を追加する。

初回だけ選択、または `mods` の隣の `resourcepacks` を自動検出。

以後はダイアログなし。

リソースパックを非常用にしても、使うたびにフォルダ選択が出るのは邪魔なので、ここは残さない。

---

# 実装を分けるならこの順番

### Phase 1 — 対応情報基盤

追加:

```text
Models/
  TranslationMapping.cs

Infrastructure/
  TranslationMappingStore.cs
```

保存先:

```text
%LOCALAPPDATA%\ModLangOrganizer\workspaces\
```

まずmappingの読み書きとatomic saveだけ作る。

---

### Phase 2 — 抽出側をmapping対応

`Executor` / `LangPathResolver` を変更。

新規抽出は、

```text
<modId>/<langfile>
```

へ。

抽出成功後、

```text
editPath
jarRelativePath
modId
archivePath
```

をmappingへ保存。

既存ファイルがあれば上書き方針は今までのものを維持する。

---

### Phase 3 — JAR反映をmapping基準へ変更

`JarLangImporter.CreatePlan()` を変更。

現在の、

```text
外部フォルダを探索
→ ファイルを列挙
→ JARパスを構築
```

から、

```text
mappingを読む
→ ファイルを確認
→ 保存済みarchivePathを使用
```

へ変更。

ここで初めて簡略フォルダとJAR内部構造を完全に切り離せる。

---

### Phase 4 — MOD更新への追従

スキャン結果とmappingを突合。

```text
旧JARなし
+
同一ModIdの新JARあり
+
namespace/lang構造一致
```

ならmappingを更新。

怪しければ自動更新せずWarning。

---

### Phase 5 — UI整理

メイン:

```text
スキャン
langを抽出
JARへ反映
```

詳細:

```text
リソースパックとして出力
```

にする。

「リソースパック出力（推奨）」という表記も外す。

---

### Phase 6 — 後方互換テスト

最低でもこのケースはテストしたい。

| ケース          | 期待動作                 |
| ------------ | -------------------- |
| 旧形式の編集フォルダあり | 移動・削除しない             |
| 新規MOD        | `<modId>/ja_jp.json` |
| アプリ再起動       | mapping維持            |
| MOD更新        | JSON維持、mappingだけ更新   |
| 同じModIdが2つ   | 衝突回避                 |
| mapping紛失    | JAR反映しない             |
| JSONだけ手動追加   | 未関連付け扱い              |
| JAR削除        | 対応切れWarning          |
| 署名対象         | JAR反映ブロック            |
| 署名対象を翻訳したい   | リソースパックへ誘導           |
| JAR反映失敗      | 元JAR維持               |
| mapping保存失敗  | 古いmapping維持          |

## 最終的なユーザー体験

最終的にはこれくらい単純にできる。

```text
① modsフォルダ選択

② スキャン

③ lang抽出

翻訳フォルダ:
├ carbonconfig/
│  └ ja_jp.json
├ curios/
│  └ ja_jp.json
└ libipn/
   └ ja_jp.json

④ JSONを編集

⑤ JARへ反映
```

内部では、

```text
carbonconfig/ja_jp.json
           ↓ mapping
carbonconfig.jar
           ↓
assets/carbonconfig/lang/ja_jp.json
```

となる。

ユーザーは `assets` も `lang` もJAR内部パスも考えなくていい。

この形なら、**元々このアプリでやりたかった「翻訳ファイルを簡単に取り出して編集して戻す」にかなり綺麗に戻せる**。リソースパックはそのフローを邪魔せず、直接変更できないMODだけ救う安全弁として残せる。
