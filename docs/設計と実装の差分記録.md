# 設計書 vs 実装 — 差分記録

> 作成日: 2026-02-25  
> 対象: 設計書 v1.3 ↔ 実装コード (main branch)  
> 目的: 設計段階で言語化・意識されていなかった実装上の判断を記録する

---

## 概要

設計書には明記されていなかったが、実装で追加・変更された項目を以下にまとめる。  
これらは「設計→実装の過程で自然に必要になった判断」や「ユーザー体験を向上させるために追加された機能」であり、設計段階で気づかなかった部分にあたる。

---

## A. 設計書になかった新機能

### A-1. langフォールバック機能

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | ターゲットのlangファイル（例: `ja_jp.json`）が出力先に存在しない場合、ソースファイル（例: `en_us.json`）をコピーして生成する機能 |
| 関連コード | `Options.LangFallbackEnabled/SourceName/TargetName`, `Executor.ApplyLangFallback()`, `AppSettings`, UI上のチェックボックスとテキスト入力 |
| 判断の背景 | Minecraft Modの翻訳作業で「まだ翻訳されていない言語ファイル」を英語ベースで生成しておきたいという実用ニーズ。設計時には「既存langの整理」だけを考えていたが、「翻訳の作業起点を作る」機能が実際には必要だった |

### A-2. 設定の永続化（SettingsService / SettingsStore）

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし**（起動ごとに初期状態を想定していた） |
| 実装 | `%LOCALAPPDATA%\ModLangOrganizer\settings.json` にJSON形式で全設定を保存・復元 |
| 含まれる設定 | TargetDir, OutputRoot, OutputRootSameAsTarget, BackupZip, CancelGranularity, LangFallback関連 |
| 関連コード | `SettingsStore`（読み書き）, `SettingsService`（デバウンス＋排他制御）, `AppSettings.Clone()` |
| 判断の背景 | GUIツールなのに毎回フォルダを選び直すのは不便。「前回の状態を覚えている」のはGUIアプリとして当然の期待だが、設計段階では意識していなかった |

#### A-2a. デバウンス保存（400ms）

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | 設定変更のたびに即座に書き込むのではなく、400msの猶予を設けて最後の変更のみを保存する |
| 判断の背景 | テキスト入力中に1文字ずつファイルI/Oが走るのを防ぐ。パフォーマンスとディスク負荷の実装上の配慮 |

#### A-2b. アトミック書き込み（temp → replace）

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | `.tmp` ファイルに書いてから `File.Replace` で差し替え。書き込み中にクラッシュしても設定ファイルが壊れない |
| 判断の背景 | 設定ファイル破損を防ぐ安全策。設計書のセキュリティ要件にはjar展開時の安全策はあったが、アプリ自身の設定保存の安全性は見落としていた |

#### A-2c. 破損設定ファイルの自動バックアップ

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | JSONパースに失敗した場合、`settings.broken.<timestamp>.json` としてバックアップしてからデフォルト値でリセット |
| 判断の背景 | ユーザーが手動編集して壊した場合や、バージョンアップで形式が変わった場合のリカバリ |

#### A-2d. 存在しない保存済みパスの検出と警告

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | 起動時に保存済みTargetDirが存在するか確認し、存在しなければ空にリセットして警告ログを出す |
| 判断の背景 | USBドライブ取り外しやフォルダ削除で保存パスが無効になるケースへの対応 |

## B. 設計書になかったUI要素

### B-1. カスタムタイトルバー

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし**（標準のウィンドウタイトルを暗黙に想定） |
| 実装 | グラデーションアイコン（⬡）、アプリ名、バージョン表示（v1.0）、jar数バッジ（📦 X jars）を含むカスタムヘッダー |
| 判断の背景 | テーマに統一感を持たせるためのビジュアル強化。情報の一目把握（jar数など） |

### B-2. ステータスバー

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | ウィンドウ下部に常時表示。状態テキスト＋ビジーインジケータ（色付きドット＋テキスト: 待機中/スキャン中/実行中） |
| 判断の背景 | ログビューだけでは「今アプリが何をしているか」が分かりにくい。常にアプリの状態を可視化するUI |

### B-3. 出力先「親フォルダと同じ場所に出力する」チェックボックス

| 項目 | 内容 |
|------|------|
| 設計書 | 「出力ルートは既定で親フォルダとし、任意変更も可能」とだけ記載 |
| 実装 | `OutputRootSameAsTarget` チェックボックスを設け、ONなら出力先テキストボックスと「変更...」ボタンを無効化し、TargetDirに自動同期 |
| 判断の背景 | 設計の「既定で親フォルダ」を具体的にどうUIで表現するかの判断。「既定値をセットする」だけでは、ユーザーが意図せず変更してしまうリスクがある |

### B-4. モダンダークテーマ（Minecraft風カラーパレット）

| 項目 | 内容 |
|------|------|
| 設計書 | テーマ/デザインに関する記載なし（WPF標準テーマを暗黙に想定） |
| 実装 | 完全カスタムのダークテーマ（500行超のTheme.xaml）。ベースカラー（#0F1117系）、アクセントカラー（紫#6C63FF / 緑#10B981）、セマンティックカラー（成功/警告/エラー/情報）、カードUI、グラデーションボタン、ドロップシャドウ等 |
| フォント | UIフォント: Segoe UI / Yu Gothic UI / Meiryo UI、等幅: Cascadia Code / Consolas |
| 判断の背景 | Minecraft関連ツールとしてのビジュアルアイデンティティ。「だたの業務ツール」ではなく「Minecraftの世界観に馴染むUI」 |

### B-5. WPFバリューコンバーター群

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | 7種のコンバーター: `BoolToVisibilityConverter`（Invertパラメータ対応）, `InverseBoolConverter`, `StatusToColorConverter`, `LogLevelToColorConverter`, `IntegrityToColorConverter`, `SnapshotStateToColorConverter`, `EnumToBoolConverter` |
| 判断の背景 | WPF MVVMパターンでUI表現を実現するために必要な実装インフラ。設計段階ではMVVMとだけ書いていたが、具体的なデータバインディングの橋渡し部分 |

### B-6. スキャン進捗と実行進捗の分離表示

| 項目 | 内容 |
|------|------|
| 設計書 | 「進捗バー（全体％ + 現在のjar名）」とだけ記載 |
| 実装 | スキャンフェーズ用と実行フェーズ用に別々のプログレスカード（Border）を表示。スキャン中は `IsScanning` で、実行中は `IsExecuting` で表示を切り替え |
| 判断の背景 | スキャンと実行は性質が異なる操作であり、同じ進捗バーを使い回すと「今何をしているか」がユーザーに伝わりにくい |

### B-7. 確認ダイアログの詳細内容

| 項目 | 内容 |
|------|------|
| 設計書 | 「実行前の確認ダイアログを必須化する」とだけ記載 |
| 実装 | ダイアログに以下を表示: 対象jar件数, 出力先パス, バックアップ有無, langフォールバック設定 |
| 判断の背景 | 「本当にこの内容で実行しますか」の確認は、具体的な情報がないと意味がない。設計では「ダイアログを出す」とだけ書いたが、何を見せるかまでは考えていなかった |

### B-8. ログListBoxの仮想化

| 項目 | 内容 |
|------|------|
| 設計書 | 「スクロール可能」とだけ記載 |
| 実装 | `VirtualizingPanel.IsVirtualizing="True"` + `ScrollUnit="Pixel"` を設定 |
| 判断の背景 | 大量Mod処理時にログが数百〜数千行になりうる。仮想化なしではUI描画がボトルネックになる |

## C. 設計書の仕様と異なる実装判断

### C-1. 出力パス構造の変更

| 項目 | 内容 |
|------|------|
| 設計書 | `出力ルート/<modid>/lang/` |
| 実装 | 単一modid: `出力ルート/<jarファイル名(拡張子なし)>/`、複数modid: `出力ルート/<jarファイル名(拡張子なし)>/<modid>/` |
| 変更理由 | jarファイル名をルートにすることで「どのjarから抽出したか」が直感的にわかる。また、異なるjarに同じmodidが含まれる場合の衝突を自然に回避できる。`/lang` サブディレクトリは省略（langファイル自体を直接配置） |
| 影響 | 設計書の「lang出力先」定義と不一致。ドキュメント上の全てのパス例が変更対象 |

### C-2. OperationPlanner の統合

| 項目 | 内容 |
|------|------|
| 設計書 | `OperationPlanner.BuildPlan(scanResult, options) -> ExecutionPlan` を独立クラスとして定義 |
| 実装 | プラン構築ロジックは `JarScanner.ScanJar()` 内に統合。`PlannedOperations` は `JarScanResult` に直接格納。`ExecutionPlan` / `JarExecutionPlan` モデルは存在するが実質未使用 |
| 変更理由 | スキャン時点でlang候補を判定しているため、その場で予定操作も構築するのが自然。別クラスに分けると二度手間になる |

### C-3. FileSystemWatcher の常時有効化

| 項目 | 内容 |
|------|------|
| 設計書 | 「任意で FileSystemWatcher を併用し」（オプション扱い） |
| 実装 | TargetDir設定時に常に `FileSystemWatcher` を起動。UIにON/OFF切り替えなし（`Options.UseWatcher` プロパティは存在するが未使用） |
| 変更理由 | jar変更検出は安全性の根幹であり、OFFにするメリットがほぼない。オプション化するとユーザーが混乱する |

### C-4. Executor の直接実行方式

| 項目 | 内容 |
|------|------|
| 設計書 | `Executor.Execute(plan, options, IProgress, CancellationToken)` — ExecutionPlanを受け取る |
| 実装 | `Executor.ExecuteAsync(List<JarScanResult>, outputRoot, options, progress, ct)` — スキャン結果リストを直接受け取る |
| 変更理由 | C-2（OperationPlanner統合）に伴い、ExecutionPlanを経由せず直接スキャン結果で実行する方が効率的 |

## D. 実装上の追加的な振る舞い

### D-1. 実行後の自動状態リセット

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | `ExecuteAsync` 完了後に `ScanCompleted = false` を設定し、再度実行するには再スキャンが必要 |
| 判断の背景 | 実行によりファイルシステムの状態が変わっているため、古いスキャン結果で再実行すると不整合が起きる |

### D-2. キャンセル時のステータス自動遷移

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | キャンセル発生時、`ModStatus.Processing` 状態のModを `ModStatus.Skipped` に一括変更 |
| 判断の背景 | UIテーブル上に「処理中」のまま残ると紛らわしい。キャンセルされたことを正確に反映する |

### D-3. Scanning / Scanned 中間ステータス

| 項目 | 内容 |
|------|------|
| 設計書 | ModStatusに `未処理/成功/警告/スキップ/失敗` を記載 |
| 実装 | さらに `Scanning`（スキャン中）, `Scanned`（スキャン済）を追加 |
| 判断の背景 | スキャンと実行が別フェーズのため、スキャン完了後〜実行前の状態を表現する必要がある |

### D-4. MainWindow の IDisposable 連携

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | `MainWindow.Closed` イベントで `DataContext` が `IDisposable` なら `Dispose()` を呼ぶ。これにより設定のフラッシュ保存と FileSystemWatcher の解放が確実に行われる |
| 判断の背景 | WPFアプリのリソース管理。設定が保存されずに終了するケースを防ぐ |

### D-5. TargetDir変更時のスキャン結果クリア

| 項目 | 内容 |
|------|------|
| 設計書 | **記載なし** |
| 実装 | `TargetDir` プロパティ変更時に `ScanCompleted = false`, `JarCount = 0` をリセットし、前のフォルダのスキャン結果を無効化 |
| 判断の背景 | フォルダ変更後に古いスキャン結果が残っていると誤操作の原因になる |

## まとめ

設計書で意識されていなかった主な観点:

1. **ユーザー体験の継続性** — 設定永続化、前回状態の復元、存在しないパスの警告
2. **翻訳ワークフローの実用性** — langフォールバック（翻訳作業の起点を作る機能）
3. **状態遷移の厳密性** — 実行後リセット、キャンセル時遷移、中間ステータス
4. **UIの「見えない部分」** — ステータスバー、確認ダイアログの内容、進捗の分離表示
5. **実装インフラ** — コンバーター群、デバウンス保存、アトミック書き込み、仮想化
6. **出力構造の実用的変更** — modidベースからjarファイル名ベースへの変更
7. **安全の粒度** — 設定ファイル自体の保護（アトミック書き込み、破損バックアップ）
8. **ビジュアルデザイン** — テーマ、カラーパレット、タイポグラフィの完全な設計
